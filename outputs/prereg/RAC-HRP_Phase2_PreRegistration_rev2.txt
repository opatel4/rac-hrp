4.  Audit — fold-level k and look-ahead
Condition 6 required confirmation that k uses training information only. The code was audited directly (engine.py, shared estimation pass).
Finding 1 — no look-ahead. k is taken from the Marchenko-Pastur count of the covariance matrix estimated on the trailing 504-day window ending at the first rebalance date, and applied forward. No observation after that date enters it. The specification is:
k_f = MPCount( Σ̂ over [t₀ − 504, t₀] ),   t₀ = first eligible rebalance of the segment
Finding 2 — the scope is wider than the name implies. The variable is initialised once per call to run(), not once per fold. Because the orchestrators pass the four development folds concatenated in a single call, k is frozen once at the first rebalance (2003) and held through 2022. The configuration option is named fixed_per_fold; the realised behaviour is fixed_per_run. Phase 0.5 reported median spec.k = 16 against a frozen k = 15.
This is not look-ahead and does not invalidate any completed result, but it is a twenty-year extrapolation from a single estimate and the name misdescribes it. A ruling is requested in §9 (R4).

6.  Correction to the separation metric
The proposed statistic included q = 1 in the candidate schedules. This makes the metric degenerate. P₁ is every eligible date, hence a superset of any trigger set, so
J(γ, q=1) = |T_γ| / |E| = f_γ   identically
and therefore J*_γ ≥ f_γ always, with the maximum attained trivially at q = 1. A placebo simulation confirms the metric carries no information in that form:

Method: 4,000 random trigger sets of the observed event count drawn without replacement from E. Recommendation: exclude q = 1 and set the pass threshold at the placebo 95th percentile of J*, recomputed at each candidate γ&apos;s own event count (≈ 0.371 at 112 events). This satisfies the requirement that the cutoff be simulation-supported rather than asserted. Note that q = 1 remains a legitimate performance comparator; it is only unusable inside this particular set-overlap statistic.

8.  Procedure — calibration is blind to performance
Performance is not merely &apos;used for nothing&apos;; it is not generated until selection is complete and recorded.
Step 1. Compute structural diagnostics only — firing, timing, VI/ARI, turnover, separation — for γ ∈ {0.5, 1.0, 1.5, 2.0}. No portfolio returns, Sharpe ratios, or drawdowns are computed or displayed.
Step 2. Apply the deterministic selection rule in §9 automatically, in code, with no human choice.
Step 3. Write the selected γ and the full diagnostic set to a frozen record (hashed, as in the Null Gate v2 manifest).
Step 4. Run the full Null Gate v2 at the selected γ. The existing gate verdict applies only to γ = 1.0 and is not inherited by any other candidate.
Step 5. Only if step 4 passes, generate performance output. Candidate-level performance may appear later in a sensitivity appendix; it is not visible when selection occurs.
9.  Deterministic selection rule
Among γ ∈ {0.5, 1.0, 1.5, 2.0}, select the value closest to the inherited γ = 1.0 that passes every hard structural criterion in §5. If two candidates are equidistant, select the larger γ, reflecting a conservative preference for fewer interventions and lower turnover.
If no candidate passes, Phase 2 stops. The &apos;least bad&apos; candidate is not selected, and the conclusion recorded is that the current trigger specification is not sufficiently informative — which would itself be a reportable finding.
Given §2 and §3, γ = 1.0 is expected to fail informativeness. The rule then evaluates γ = 1.5 next. That ordering follows from the frozen rule and from distance to the inherited value — not from any performance quantity.

11.  New ruling requested
R4 — scope of the frozen k
Should k be frozen once per run (as built — a single 2003 estimate held to 2022), or re-estimated at the start of each development fold from that fold&apos;s own trailing window (as the name fixed_per_fold implies)? Neither introduces look-ahead. Preparer&apos;s view: retain the as-built per-run freeze for Phase 2, because changing it alters the RAC-HRP configuration that the completed null gate validated, and rename the option to fixed_per_run so the record is accurate. Per-fold re-estimation may be added later as a registered robustness variant.
